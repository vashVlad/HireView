Verified live against real data (read-only, no writes) — candidate id=682's stored `"www.linkedin.com/in/amen-wolde-790a79272"` now renders as `href="https://www.linkedin.com/in/amen-wolde-790a79272"`. `tsc` clean, all 11 tests pass. Not on the do-not-touch list, committed and pushed directly to `main` — same "un-breaks a currently-broken production feature, don't hold for a PR" call as the rescreen-timeout hotfix immediately above.

**Separate, smaller issue spotted in the same data sample, not fixed:** one row's `linkedin_url` was the literal string `"LinkedIn"` (a garbled extraction, not a URL at all — id=794). **2026-07-15 — CORRECTION to every "bash-mount staleness" entry below: the bash sandbox path is NOT a disposable mirror — writes to it land on Vlad's real file, with only a read-side sync lag.** This was discovered the hard way: a `cat >>` append to `app/candidates/page.tsx`, done to "fix" what looked like tail-truncation in the bash view, duplicated the file's closing `);`/`}` in the REAL file — confirmed by Vlad's own Next.js dev server erroring on it ("Expression expected... line 602"). The correct model: bash's *read* of a just-edited file can lag behind the Edit/Write tool's real, immediate write (by seconds, sometimes longer) — but bash's *writes* apply to the same real file, not a scratch copy. So appending content because bash's view looked short was, in this one case, appending onto a file that was already complete — the lag had resolved on the read side by the time `Read` was called moments earlier, but I mistook "Read shows more than bash's tail" as proof bash was serving stale content, when here it (partly) meant the opposite: bash just hadn't caught up to displaying what was already fully and correctly written.
**Corrected procedure going forward:** (1) NEVER use `cat >>`/`sed -i` to patch what looks like a truncated tail based on a bash `tail`/`wc -l` mismatch against `Read`. (2) If `tsc` reports an error in a just-edited file, first just wait (10-30s) and re-run `tsc` — do not touch the file via bash. (3) If a full heredoc rewrite (`cat > file <<EOF`) is truly necessary, only ever use it to write the EXACT content a fresh `Read` just showed (idempotent overwrite — safe even if bash's cache was stale, since it fully replaces content rather than appending to an assumed-truncated base). (5) After any bash write to a real file this session, verify the result via a fresh `Read`, not another bash command. This session did 12 bash write operations to "fix" perceived staleness; a post-hoc audit (fresh `Read` on every file's tail) found only ONE was actually corrupted this way (`app/candidates/page.tsx`, fixed via the `Edit` tool directly) — the other 11 were, in retrospect, likely genuine reads of a real, momentarily-lagging bash cache and the writes were harmless/correct. **2026-07-10 — Auto-fired fit checks are serialized through a single-flight queue (`fitQueueRef` in `ScreenTab`), not fired in parallel per card.**
A batch of several below-threshold "promising" candidates auto-firing simultaneously would create a burst of concurrent Claude calls right after a bulk screening completes — each cross-project-fit check itself does up to 3 concurrent sub-calls, so N promising cards firing at once multiplies fast. A simple promise-chain queue (`fitQueueRef.current = fitQueueRef.current.then(run, run)`) bounds this to one cross-project-fit request in flight at a time, shared across every card on the page, regardless of whether it was auto-fired or manually clicked.

**2026-07-10 — `GET /api/cross-project-fit` reuses the exact same `getUserTeamIds()` scoping as the POST handler in the same file, not `/api/projects`' `teamIdsFilter()`.**
`/api/projects` uses `teamIdsFilter()`, which returns `undefined` for admin (sees all teams). If the eligibility count had reused that route, an admin could see "other active projects: 3" from `teamIdsFilter`'s everything-view while the real POST check (deliberately always team-scoped, see the earlier 2026-07-10 entry on cross-project fit) came back empty — a visible inconsistency.
